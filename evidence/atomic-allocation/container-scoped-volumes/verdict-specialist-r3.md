## Findings

1. **Blocking — a reused anonymous-volume name can pass validation and be deleted, and validation is not atomic with deletion.** `src/backends/ownership.ts:269-274` inspects a volume by name, compares `Name`, `CreatedAt` and the anonymous label, then launches `docker volume rm <name>`. In the reviewed Docker evidence, volume `CreatedAt` has one-second resolution. If a trusted agent removes the retained original and recreates the same anonymous-labelled name within that same second, every comparison succeeds and clean deletes the unreceipted replacement, then permits retirement. That is a demonstrated code path to the exact peer/foreign-object deletion the contract forbids, not merely an absence-of-tests concern. The regression deliberately waits for the next second before creating its replacement, so it proves only the different-timestamp case (`scripts/allocation-rehearsal.ts:422-430`).

   The same lines have a second interleaving: after the inspect returns, another trusted agent can remove the original and recreate the name at a later timestamp before the owned `docker volume rm` executes. The command still deletes the replacement by name. Thus strengthening only the timestamp comparison cannot close the class. The current regression covers replacement before inspect, not replacement between inspect and execution. The author's “same-name/same-second replacement not qualified” disclosure does not satisfy the supplied guarantee, and the inspect/remove race is not excluded by the stated non-hostile threat model.

   Distinguishing checks are to create the replacement in the original's timestamp second and assert that clean preserves it and retains claims, and to pause the owned delete after inspection, replace the volume, then assert the same. Holding this guarantee requires an ownership/deletion construction that covers both interleavings. Otherwise the owner must explicitly narrow and accept the supported external-mutation contract as a waiver; silently treating these trusted-local races as hostile or impossible would change the supplied scope.

2. **Should fix — a crash after a successful retry can permanently strand a failed deletion receipt even though the child is absent and the successful completion is durable.** A failed anonymous-volume delete is reconciled only when a later successful `runOwnedCommand` reaches `reconcileDeletion` (`src/core/owned_command.ts:134-140`, `src/core/lease_store.ts:359-370`). Suppose the first delete reports in-use, the borrower is removed, and the retry's executor durably records exit 0, but the CLI crashes before `reconcileDeletion`. On recovery, the volume is absent, so `deleteAnonymousVolumes` skips it without executing or reconciling anything (`src/backends/ownership.ts:267-269`). The generic loop reconciles the successful exit-0 launch but not the earlier nonzero launch, and `down` throws `CLEANUP_REQUIRED` for that old receipt (`src/commands/down.ts:60-68`). Every later clean repeats this path; forced reallocation also rejects unresolved launches (`src/core/lease_store.ts:639-650`). There is no public recovery path, despite exact absence and a durable successful retry.

   Add a regression that holds the owner after the retry's durable completion but before reconciliation, then requires the next clean to retire with claims released and no additional deletion of an absent/replacement object. Recovery should fold matching durable successful deletion facts through the common reconciliation rule rather than requiring a fresh deletion command; patching only the anonymous-volume branch would leave the same crash class in the other exact-delete paths.
