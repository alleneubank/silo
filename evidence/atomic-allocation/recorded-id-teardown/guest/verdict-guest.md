No behavioral failure was observed in the required scenarios.

What worked: the cleanup model was observable from `status --json`; the Compose ownership labels and explicit project-name example made fixture setup straightforward. A broken Tiltfile did not affect cleanup. Residual foreign ownership refused consistently and retained all claims rather than silently adopting the object. Repeated cleanup was predictable.

Papercuts: adding only `TILT_HOST` under `[hosts]` caused `hosts must include APP_HOST` on my first CI attempt. Adding the APP_HOST shown in the full configuration example resolved it; the error was clear and no project was allocated. Forbidden hook errors are verbose schema-validator JSON, even in the human-facing message; the hook docs explained the intended restriction more directly. Neither prevented completion.

Hesitations: “residual container ...; claims retained” named the blocking object clearly. Resolving it required independent exact-ID ownership knowledge, which the supplied fixture ledger provided. For real work, an operator would need the same owner confirmation rather than deleting by project name.

Looks: CLI-only trial; no visual UI review requested or performed. Both live Tilt HTTP endpoints returned200, but browser rendering was not assessed. Tilt emitted transient internal resource-already-exists reconciler errors during initial local-resource startup; both intended listeners started and responded, so these did not block the tested flow. Raw output is preserved in own-up.log and peer-up.log.

Trust: these observed outcomes support using this cleanup model for a disposable Compose/local-resource workspace. This run does not establish production, Kubernetes, credentials, hostile concurrent replacement, crash durability, or arbitrary trusted Tiltfile safety.
